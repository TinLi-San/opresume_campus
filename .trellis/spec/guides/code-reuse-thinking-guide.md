# 代码复用思维指南

> **目的**：在创建新代码前停下来思考 - 它是否已经存在？

---

## 问题所在

**重复代码是不一致性 bug 的头号来源。**

当你复制粘贴或重写现有逻辑时：
- Bug 修复无法传播
- 行为随时间发散
- 代码库变得更难理解

---

## 编写新代码前

### 步骤 1：先搜索

```bash
# 搜索相似的函数名
rg "functionName"

# 搜索相似的逻辑
rg "关键词"
```

### 步骤 2：问自己这些问题

| 问题 | 如果是... |
|------|----------|
| 是否存在类似函数？ | 使用或扩展它 |
| 这个模式是否在其他地方使用？ | 遵循现有模式 |
| 这是否可以成为共享工具？ | 在正确的位置创建它 |
| 我是否在从另一个文件复制代码？ | **停止** - 提取到共享位置 |

---

## 常见重复模式

### 模式 1：复制粘贴函数

**❌ 不好**：将验证函数复制到另一个文件

**✅ 好**：提取到共享工具函数，在需要的地方导入

### 模式 2：相似组件

**❌ 不好**：创建一个与现有组件 80% 相似的新组件

**✅ 好**：通过 props/变体扩展现有组件

### 模式 3：重复常量

**❌ 不好**：在多个文件中定义相同常量

**✅ 好**：单一数据源，到处导入

---

## 何时抽象

**应该抽象的情况**：
- 相同代码出现 3+ 次
- 逻辑足够复杂，可能有 bug
- 多人可能需要它

**不应该抽象的情况**：
- 只使用一次
- 简单的一行代码
- 抽象会比重复更复杂

---

## 批量修改后

当你对多个文件做了类似修改后：

1. **检查**：是否捕获了所有实例？
2. **搜索**：运行 `rg` 查找任何遗漏
3. **考虑**：是否应该抽象？

---

## 陷阱：产生相同输出的不对称机制

**问题**：当两个不同机制必须产生相同文件集时（例如，初始化时的递归目录复制 vs 更新时的手动 `files.set()`），结构变化（重命名、移动、添加子目录）只能通过自动机制传播。手动机制会悄无声息地偏离。

**症状**：初始化工作正常，但更新在错误路径创建文件或完全遗漏文件。

**预防检查清单**：
- [ ] 迁移目录结构时，搜索所有引用旧结构的代码路径
- [ ] 如果一个路径是自动派生的（glob/copy），另一个是手动列出的，手动的需要更新
- [ ] 添加回归测试，比较两个机制的输出

## 提交前检查清单

- [ ] 没有应该共享的复制粘贴逻辑
- [ ] 常量在一个地方定义
- [ ] 相似模式遵循相同结构
